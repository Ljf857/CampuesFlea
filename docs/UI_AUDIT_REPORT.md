## 关于本报告

### 方法

本报告分两轮完成，两轮的关系是**互相验证**而非简单叠加：

- **第一轮（代码审计）**：通读全部界面源码与设计系统，量化统计跨文件的不一致，形成问题假设。此轮不含任何"观感"判断。

**第一轮的假设绝大多数被截图证实**（详见 3.4 节），这是本报告可信度的主要来源。

### 局限

以下三类结论本报告**无法给出**，需要更多材料：

1. **对比度数值**：所有对比度判断均为视觉估计，未做像素级测量。涉及具体 WCAG 比值的地方（如分类图标白字叠浅色块）需实测。

## 一、执行摘要

### 一句话结论

**这个 App 的问题不是"设计得不好看"，而是"声明了一套系统，然后系统性地绕过了它"。** 字号、圆角、语义色、形状、状态色、表单范式、深色表面色阶——每一套都被定义了，每一套都没被执行。所有具体问题几乎都能回溯到这一个根因。

### 最该优先处理的七件事

| # | 问题 | 为什么它排在前面 |
|---|---|---|
| 1 | **中文用衬线体渲染** | 影响 100% 界面的每一个字；修复成本极低；是答辩现场的第一印象 |
| 2 | **键盘遮挡提交按钮** | 已实锤：验证码登录页按钮被遮 80%。注册页/发布页输入更多且不可滚动，问题会更严重 |
| 3 | **表单状态零保存** | 发布商品填写成本最高，转屏/切后台/误触返回即全部清空，丢一次用户就不会回来 |
| 4 | **七个页面缺加载/空/错误态** | 用户看到白屏的第一反应是"App 坏了"而不是"我还没收藏" |
| 5 | **验证码明文泄露给用户** | 4 处调试残留上线，短信验证形同虚设；答辩必被问到 |
| 6 | **深色模式表面色阶失效** | 根因明确（背景色与表面色取同一个值），导致深色下"卡片"这个概念整个消失 |
| 7 | **六个提交按钮无防重复** | 会直接产生重复商品/重复订单，属于业务脏数据 |

### 关键数字速览

| 指标 | 实测 | 含义 |
|---|---|---|
| 硬编码字号 : 主题字号引用 | **83 : 22** | 类型系统被绕过约 4 倍，且混入 10/11/13/15sp 四个体系外尺寸 |
| 硬编码圆角 : 主题圆角引用 | **69 : 4** | 7 种圆角取值散落各处 |
| 语义色 token 引用数 | **0**（共 5 个 token） | PriceColor / StarColor / SuccessColor / WarningColor / DividerColor 全部为死代码 |

## 二、审计报告

### 2.1 视觉

**核心判断：有两套视觉语言在打架，且没有一套被执行到底。**

App 内置了一套自建的"玻璃拟态"系统（`ui/components/Glass.kt` 提供 `glassTint` / `glassBorder` / `glassShadowBrush` / `GlassSurface` / `GlassTopBar` / `GlassCard` 六件套），但落地程度极低：

| 组件 | 自定义玻璃版 | 原生 Material 3 版 |
|---|---|---|
| 卡片 | `GlassCard` **4 处** | `Card` **26 处** |
| 顶栏 | `GlassTopBar` **25 处** | `TopAppBar` **0 处** |

即：**真正在用的"玻璃"只有顶栏一个。**

#### 玻璃拟态在这套实现里不成立

玻璃卡片底色是 `surface` 的 0.68 透明度，叠在 `background`（`#F8F9FC`）上——混色结果与 `surface` 几乎无法区分。真正让卡片"浮起来"的是那圈 1dp 描边和 2dp 阴影，不是玻璃。**玻璃拟态依赖背后有内容或色彩可折射，这里背后什么都没有**，于是退化成"带描边的普通卡片"。

同理，**底栏的玻璃同样没生效**：底栏自身是 78% 透明度的 `surface`，但 `NavGraph.kt:218` 用 `innerPadding` 把内容整体抬到了底栏之上，没有任何内容从底栏下方滚过。78% 的白叠在 92% 的白上，肉眼与纯色无异。而底栏上方还额外加了 10dp 渐变投影 + 1dp 分隔线（`NavGraph.kt:95-96`）——**这层渐变在截图中表现为一条明显的灰色污迹带**，在任何浅色背景上都像渲染瑕疵，而非"立体感"。

#### 分类色板与品牌完全脱节

首页首屏最抢眼的视觉元素是 8 个分类色块：绿、蓝、玫红、橙红、紫、橙、玫红、灰。颜色来自服务端字段（`GoodsModels.kt:69-76` 由 hex 解析），**8 个分类 7 种颜色，无任何语义逻辑，也与品牌主色 `#0077FF` 无关**。其中"其他"被赋予灰色，视觉上呈禁用态。

在深色模式下问题加剧：这些高饱和色块铺在纯黑背景上，成为整屏最亮最刺眼的元素（见 2.7 节）。

#### 形状语言冲突

- 输入框一律**近直角描边**（4-8dp），按钮一律**全圆角胶囊**——两套形状语言并存于同一屏
- 按钮内部也不统一：`登录` 实心、`验证码登录` 描边
- 聊天气泡：自己的消息**实心蓝**、对方的消息**白底描边**——同一组件的两种截然不同的成形方式
- 搜索框：首页为 **8dp 方角**，搜索页为 **近胶囊圆角**

#### 字体：中文衬线体（本报告最重要的一条视觉发现）

**所有中文以衬线体（宋体风格）渲染，而数字与拉丁字母为黑体。**

对照：`商品详情`、`实名认证`、`找回密码`、`立即购买` 等中文有明确的笔画粗细对比与三角衬角；而同一行内的 `178****8569`、`v1.0.0`、`CF202606251823233858`、`2026-09-07 15:33:17`、`21.2 MB` 为干净的黑体。

**"中文衬线 + 西文黑体"正是 CJK 字体回退失败的特征**：拉丁字符命中 Roboto，中文字符回退到了一个衬线 CJK 字体。根因：项目 `app/src/main/res/` 下**没有 `font` 目录**，且 `ui/theme/Type.kt` 全部使用 `FontFamily.Default`——App 从未指定字体族，中文排版完全交给设备决定。

这条不阻断任何任务，但它出现在每一个界面的每一个字上，让 App 看起来像一份打印表格而非现代移动应用。且它意味着**排版不可控**：换设备或换 ROM，字体可能再次改变。

### 2.2 层级

#### 字号阶梯是倒挂的

`ui/theme/Type.kt` 中：

- `titleLarge` = 22sp
- `headlineLarge` = 20sp
- `headlineMedium` = 18sp

**title 比 headline 还大**，与 M3 的语义约定相反。任何"页面标题用 titleLarge、区块标题用 headlineMedium"的写法，都会得到"区块标题比页面标题小、页面标题比大标题还大"的错乱结果。

同时整个阶梯极度压缩：16sp 同时是 `titleMedium` 和 `bodyLarge`，14sp 同时是 `titleSmall` / `bodyMedium` / `labelLarge`，12sp 同时是 `bodySmall` / `labelMedium`。**相邻层级只差 1-2sp，靠字号已无法拉开层级**，只能靠字重和颜色硬撑。

更根本的是这套阶梯也没被使用：**83 处硬编码 `fontSize`，仅 22 处引用 typography**，且硬编码中出现 10 / 11 / 13 / 15sp 四个体系里不存在的字号。首页单屏内即出现 12/13/14/15/16/18sp 六种字号（`HomeScreen.kt:90,96,154,168,169,231,232`），全部是就地决定的数字。

#### 卡片内部信息是平的

商品卡（`HomeScreen.kt:218-242`）：标题 14sp、价格 16sp、校区 12sp、成色 12sp——价格之外没有主次；成色标签与校区使用了相同的视觉重量。

#### 状态层级完全缺失

订单的五种状态（待付款 / 已付款 / 已发货 / 已完成 / 已取消）在列表页（`MyOrdersScreen.kt:48`）与详情页（`OrderDetailScreen.kt:35`）**全部用同一个 `primaryContainer` 渲染**。五个状态视觉完全一致，用户扫列表无法区分"待办"与"已结束"。

截图佐证：`我的订单` 页中"已取消"标签为浅蓝底蓝字，与商品详情页的"已认证"、商品卡的"9成新"用的是同一个容器色。深色模式下这个标签变为亮蓝色，成为整张卡片最亮的元素——**一个表示"已取消"的标签，视觉权重高于"待付款"**。

讽刺的是 `Color.kt:30-31` 专门定义了 `SuccessColor` 与 `WarningColor` 就是为此场景准备的，但零引用。

### 2.3 导航

#### 做对的部分

整体骨架合理：Splash → Main（4 tab + 中央发布按钮）→ 26 个子页，子页一律 `GlassTopBar` + 返回箭头。**这是全 App 唯一真正一致的元素**。首页滚动时顶部搜索栏保持固定（只有 banner、分类、商品滚动），这是正确的做法。

#### Tab 切换丢状态

四个 tab 均使用 `popUpTo(Home)` 且未保存/恢复状态（`NavGraph.kt:117-121` 等四处）。从"我的"切到"分类"再切回，滚动位置、列表数据、筛选条件全部重置。二手交易的核心动作是"逛—比较—回退再逛"，这个损失很直接。

#### 认证流程：4 个入口 = 3 套头部 + 5 种返回策略

| 页面 | 头部样式 | 返回策略 |
|---|---|---|
| 登录 | 居中图标 + 标题 + 副标题 | 回退，否则跳主界面（`LoginScreen.kt:44`） |
| 验证码登录 | 居中图标 + 标题 + 副标题 | 回退上一级 |
| 注册 | 左对齐裸标题 | 回退上一级 |
| 找回密码 | 左对齐裸标题 | **无兜底**（`ResetPasswordScreen.kt:46`） |

另有 `VerifyScreen.kt:110`、`ChangePasswordScreen`、`ChangePhoneScreen` 同样**无兜底**。**这四处从深链进入时返回键是死的。**

#### 真正的死链接

- 关于页四行（用户协议 / 隐私政策 / 给我们评分 / 版本更新，`AboutScreen.kt:30-31`）：onClick 为空实现——**可点、有涟漪、有按钮语义、带 `>` 箭头，但什么都不发生**
- 商品详情"进店"、"分享"：仅弹 Toast（`GoodsDetailScreen.kt:106,70`）
- 下单页运费写死 `¥0.00`（`CreateOrderScreen.kt:86`）
- 反馈页存在 images 字段但无上传入口（`FeedbackScreen.kt:50`）
- 关于页联系方式为假数据（`400-000-0000`、`service@xxx.com`，`AboutScreen.kt:34`）

**"看起来能用实际不能用"比明显的"敬请期待"更伤信任。**

### 2.4 状态

**这是全项目最薄弱的一环，可以概括为"没有状态设计"。**

#### 列表页三态（加载/空/错误）覆盖情况

| 覆盖度 | 页面 |
|---|---|
| 三态齐全 | 首页（骨架屏 + 空态 + 错误 + 重试）——唯一 |
| 部分 | 历史页（仅空态）；搜索结果页（错误仅文字、无重试）；商品详情页（加载失败**白屏**，`:55-60` 仅 Toast 无兜底分支）；订单详情页（加载中**白屏**，`:33` 直接 `detail?.let`） |
| **完全没有** | **分类页、收藏页、我的商品页、消息页、通知页、我的订单页** |

空数据时的直接表现是**顶栏之下一片空白**（`FavoriteScreen.kt:27`、`MessageScreen.kt:57`、`MyOrdersScreen.kt:45` 等）。用户无法区分"没有数据""还在加载""加载失败"。

截图实锤：深色模式下的聊天空会话页（`aee12537`）是**整屏纯黑**，无任何占位文案。

#### 加载样式两套且互相打架

首页用骨架屏，其余全部用转圈（搜索结果 `:65`、商品详情 `:62`）。且**骨架屏与真实卡片使用不同的容器组件**——骨架用不透明的 `Card`（`SkeletonCard.kt:46`），真实用半透明玻璃卡 + 描边，加载完成瞬间卡片外观会跳变。

#### 反馈层从未被设计

**Toast 92 处，Snackbar 0 处。** 这个比例说明反馈层没有经过设计，全部甩给系统。后果：

- 没有撤销能力
- 读屏无法稳定播报
- 不能携带操作按钮
- 位置固定在屏幕底部，与玻璃底栏、手势条区域重叠
- 无法承载"是哪个字段错了"这类需要定位的信息

#### 错误信息笼统且与出错字段脱钩

全 App 仅 2 处行内错误（`RegisterScreen.kt:67,69`，且均为密码长度校验），其余一律底部 Toast，文案多为"操作失败"级别。用户在注册页填错手机号，提示出现在屏幕底部，内容是服务端返回的原始字符串。

#### 提交态参差

| 页面 | 置灰 | 转圈 |
|---|---|---|
| 登录 / 验证码登录 | ✓ | ✓ |
| 注册 / 找回密码 | ✓ | ✗ |
| **修改密码 / 修改手机号** | **✗** | **✗** |

后两者存在真实的重复提交风险。

#### 破坏性操作全部无确认、无撤销

退出登录（`MineScreen.kt:109`、`SettingsScreen.kt:83`）、取消订单（`MyOrdersScreen.kt:63`）、确认收货（`:64`、`OrderDetailScreen.kt:46`）、清空聊天记录（`ChatScreen.kt:116`）、删除地址（`AddressListScreen.kt:37`）、删除已上传图片（`PublishGoodsScreen.kt:196`、`EvaluateScreen.kt:99`、`ReportScreen.kt:91`）——全部点击即执行。

其中**删除地址与"编辑"按钮并排等大、仅靠文字颜色区分**；删图片的 × 点击区仅 16-24dp。

#### 聊天无发送态

文本消息发出后直接清空输入框（`ChatScreen.kt:157`），失败仅弹 Toast 而草稿已丢失。没有"发送中 / 已发送 / 失败重试"，`MessageInfo.isRead` 字段存在但 UI 从不渲染已读回执。新消息到来时无条件强制滚动到底（`ChatScreen.kt:106`），用户正在上翻历史时会被强行拽回。

### 2.5 无障碍

#### 触控目标小于 48dp（15 处以上）

| 位置 | 实际尺寸 | 证据 |
|---|---|---|
| 首页消息入口 | ~24dp | `HomeScreen.kt:100` |
| 搜索页"搜索" / "清空" | 纯文字可点，≈行高 | `SearchScreen.kt:82,89` |
| 搜索页热词行 | ~40dp | `SearchScreen.kt:96` |
| 删除已上传图片 × | 16-18dp | `PublishGoodsScreen.kt:196` 等 3 处 |
| 头像编辑入口 | 28dp | `EditProfileScreen.kt:131` |
| 我的订单操作按钮 | 36dp | `MyOrdersScreen.kt:63-65` |
| 首页搜索框高度 | 40dp | `HomeScreen.kt:92` |

#### 图片描述基本为空

`contentDescription = null` 共 **17 处**，有意义的描述仅 **7 处**。商品封面、banner、实名认证的证件照（`VerifyScreen.kt:226`）、聊天图片、聊天头像全部无描述。

#### 表单无障碍几乎为零

42 个输入框中：

- **无一处 autofill / 密码管理器语义**（用户换机后无法自动填充，直接影响登录转化）
- **无一处 IME action**（回车不会跳到下一格或提交）

### 2.7 深色模式（专项）

深色模式是本轮新增的走查维度，问题数量超出预期。

#### 表面色阶失效 —— "卡片"这个概念在深色下消失

对比「设置」页的浅色与深色截图：浅色下每个分组是**明确的白色卡片浮在浅灰背景上**；深色下卡片与页面背景**几乎无色差**，整个列表塌成一片，只剩分隔线勉强划分。

根因在代码里，且很干净：

- `Color.kt:45` `DarkBackground = 0xFF1A1C1E`
- `Color.kt:47` `DarkSurface  = 0xFF1A1C1E`

**两个值完全相同。** 浅色模式的 `#F8F9FC` vs `#FDFBFF` 尚有一丝差异（截图可见），深色模式直接归零。

雪上加霜：`Color.kt:51-52` 定义了 `DarkSurfaceContainerLow = #232528` / `DarkSurfaceContainerHigh = #2A2C2F`，但 `Theme.kt:19-27` 的 `darkColorScheme` **根本没有把它们传入**——这两个 token 同样是死代码。

结果：深色模式下所有分层只能依赖那圈 1dp 描边，而描边正是"玻璃卡退化"的产物。**一个靠描边撑起来的界面，在深色下会显得极其平面。**

#### 系统导航栏不跟随 App 内深色主题（15 / 15 复现）

**每一张深色截图的最底部，系统导航条都是浅灰白底 + 深色图标**，而 App 是纯深色，形成一条横贯屏幕底部的浅色带。

根因：`MainActivity.kt:19` 的 `enableEdgeToEdge()` 默认按**系统**主题决定系统栏样式，而 App 内主题由 `ThemePreferences` 独立设置。用户"系统浅色 + App 内深色"时必然割裂。

这是每一页、每一时刻都存在的视觉裂缝，影响面大于任何单页问题。

#### 系统键盘不跟随 App 内深色主题

`595f7a8d`（修改手机号，深色）截图显示：**App 深黑、键盘纯白**。输入法由系统控制，App 无法修改——但它意味着"强制深色模式"会带来一整块浅色割裂区域。这是 Android 上的普遍现象，不必强行修复，但需知悉。

#### 分类色在深色下变成霓虹

首页深色截图：8 个高饱和分类色块铺在纯黑背景上，成为整屏最亮最刺眼的元素。颜色来自服务端且无暗色变体，App 只能原样渲染。

#### 亮色 banner 在深色下刺眼

首页"数码好物 学生专享"营销图为高明度蓝白色调，在深色模式下成为一块发光板，与"深色模式降低亮度"的初衷直接冲突。

#### 选中态降级

「我的订单」的 tab：浅色模式下选中项为**蓝色文字 + 下划线**；深色模式下**三个 tab 文字全为白色**，选中态只剩一条下划线。用户需仔细辨认下划线位置才能确认当前 tab。

#### 深色模式的正面结论

「设置」「关于我们」「意见反馈」「主题模式」几页在深色下**比浅色下更好看**——输入框描边、分隔线、浅蓝图标在深色背景上对比清晰，层次反而更明确。

这说明**深色模式的底子是对的，缺的是表面色阶与系统栏同步这两块，不需要推倒重来**。

> 编号规则：P0 阻断核心任务或造成数据/信任损失；P1 体验断层与一致性崩坏；P2 打磨项。

### 3.1 P0 · 阻断核心任务或造成数据/信任损失（7 项）

---

**P0-1｜验证码明文泄露给用户**

**【证据】** 4 处 Toast 直接显示验证码并自动填入输入框：`SmsLoginScreen.kt:37`、`RegisterScreen.kt:49`、`ResetPasswordScreen.kt:41`、`ChangePhoneScreen.kt:38`。

**【为什么】** 开发调试残留上线。用户看到自己的验证码且输入框被自动填好——短信验证这道关卡形同虚设。任何一次答辩演示都可能被问到，且属于安全问题而非体验问题。

**【建议】** 移除全部验证码回显与自动填充。验证码只能通过短信到达用户手机。如需演示便利，限定在 debug 构建且默认关闭。同时检查后端是否也在响应体中返回验证码——若是，一并要求后端停止下发。

---

**P0-2｜键盘遮挡输入框与提交按钮**（已由截图确认）

**【证据】**
- 全 App **42 个输入框，仅 1 处键盘避让**（`ChatScreen.kt:108`）
- `AndroidManifest.xml` 未设置 `windowSoftInputMode`
- 登录、注册、找回密码、修改密码、修改手机号、实名认证的表单均为**不可滚动的固定 Column**（`LoginScreen.kt:43`、`RegisterScreen.kt:60`、`ResetPasswordScreen`、`ChangePasswordScreen.kt:36`、`ChangePhoneScreen.kt:43`）
- 下单页提交按钮固定在底部而备注框在滚动区内（`CreateOrderScreen.kt:88-94`）
- **截图实锤**：`ca87244d`（验证码登录页）键盘弹出后，「登 录」按钮仅露出顶部约 20%，「还没有账号？立即注册」100% 被遮挡

**【为什么】** 这是"任务无法完成"级缺陷。注意该页**只有 2 个输入框**就已如此；注册页（5 个输入框 + 协议 + 按钮）与发布页（5 个输入框 + 成色滑块 + 单选组）内容更多且不可滚动，提交按钮会被完全遮死，用户只能靠先收起键盘再点击——而很多用户不知道可以收起键盘。

**【建议】** 将键盘避让定为全局规则而非逐页处理：表单页统一可滚动 + 底部预留键盘高度安全区；下单页提交按钮改为跟随内容滚动或固定在键盘上方。同时为每个输入框补上键盘类型与"下一项/完成"回车行为（当前 42 个输入框一个都没有）。

---

**P0-3｜表单状态零保存，返回键不拦截未保存内容**

**【证据】** `rememberSaveable` **0 处**，`remember` **97 处**；发布商品（`PublishGoodsScreen.kt:185`）、编辑资料（`EditProfileScreen.kt:114`）、编辑地址、意见反馈（`FeedbackScreen.kt:71`）的返回箭头直接丢弃全部已填内容。

**【为什么】** 发布商品是 App 的核心动作，填写成本最高（标题 + 价格 + 原价 + 描述 + 最多 9 张图）。填到一半转屏、切出去回消息、或误触返回，内容全部蒸发。丢失一次，用户不会有第二次。

**【建议】**
1. 所有表单字段状态改为可跨配置变更与进程重建存活
2. 页面存在未提交改动时，返回操作先弹确认（"放弃已填写的内容？"），并提供"存草稿"
3. 发布页额外做本地草稿，下次进入自动恢复

---

**P0-4｜七个页面缺加载/空/错误态，表现为白屏**

**【证据】** 完全没有三态：**分类页、收藏页、我的商品页、消息页、通知页、我的订单页**；商品详情页加载失败白屏（`GoodsDetailScreen.kt:55-60` 仅 Toast 无兜底分支）；订单详情页加载中白屏（`OrderDetailScreen.kt:33` 直接 `detail?.let`）；聊天与订单详情的 ViewModel 中有 `isLoading` 但 UI 从不消费（`ChatViewModel.kt:31`）。**截图实锤**：深色聊天空会话页（`aee12537`）整屏纯黑。

**【为什么】** 白屏无法自证。用户看到白屏的第一反应是"App 坏了"然后卸载，而不是"我还没有收藏"。这是 App 专业度的分水岭，也是最容易被答辩追问的地方。

**【建议】** 把"四态齐全"作为所有数据页面的验收标准，逐页补齐：
- 加载态给出**与最终布局同构**的骨架，避免加载完成的跳变
- 空态给出**可行动的**引导（收藏页应是"还没有收藏，去逛逛 →"而非"暂无数据"）
- 错误态给出具体原因 + 重试按钮

首页已是唯一做全的样板，将其抽成统一规范推广到其余页面。

**P0-5｜六个提交按钮无防重复提交**

**【证据】** 发布商品（`PublishGoodsScreen.kt:186` 的 enabled 仅跟踪图片上传，不管发布请求本身）、编辑资料（`:116`）、编辑地址（`EditAddressScreen.kt:31`）、提交订单（`CreateOrderScreen.kt:88`）、修改密码（`ChangePasswordScreen.kt:43-53`）、修改手机号（`ChangePhoneScreen.kt:48-53`）——请求进行中既不置灰也不显示加载。

**【为什么】** 直接产生业务脏数据。连点两下"发布"发出两个商品，连点两下"提交订单"即两笔订单。二手交易中重复订单需要人工介入。项目内 `EvaluateScreen` / `ReportScreen` / `FeedbackScreen` 已经写对了，说明团队知道怎么做，只是没有统一执行。

**【建议】** 规定所有提交型按钮必须满足三条：请求期间置灰、按钮内显示进行中状态、逻辑层再做一次幂等拦截（防止快速双击绕过 UI 状态）。把已做对的三个页面定为参照实现。

---

**P0-6｜破坏性操作全部无确认、无撤销**

**【证据】** 退出登录（`MineScreen.kt:109`、`SettingsScreen.kt:83`）、取消订单（`MyOrdersScreen.kt:63`）、确认收货（`:64`、`OrderDetailScreen.kt:46`）、清空聊天记录（`ChatScreen.kt:116`）、删除地址（`AddressListScreen.kt:37`）、删除已上传图片（`PublishGoodsScreen.kt:196`、`EvaluateScreen.kt:99`、`ReportScreen.kt:91`）——全部点击即执行。删除地址与"编辑"按钮并排等大，仅靠文字颜色区分。

**【建议】** 分两级处理：
- **不可逆且损失大**的（退出登录、取消订单、删除地址、清空聊天）用确认弹窗，且**按钮文案必须写清后果**（"确定取消这笔订单吗？取消后无法恢复"），而非通用的"确定/取消"
- **可逆或可低成本重建**的（删图片）不用弹窗打断，改为操作后给一个带"撤销"的提示条

所有需确认的危险操作，按钮应放在远离主操作处并降低视觉权重——当前删除与编辑一样大是反的。

---

**P0-7｜中文使用衬线体渲染**

**【证据】** 46 张截图中的全部中文均为衬线体（宋体风格），而同屏内的数字与拉丁字母为黑体。项目 `app/src/main/res/` 下**无 `font` 目录**；`ui/theme/Type.kt` 全部使用 `FontFamily.Default`。

**【为什么】** 它出现在每一个界面的每一个字上，让 App 看起来像一份打印表格而非现代移动应用。这是答辩现场的第一印象。同时意味着排版不可控——换设备或换 ROM，字体可能再次改变。**这是全项目中修复成本最低、观感收益最高的一条。**

**【建议】** 随包内置一套中文黑体（思源黑体 / Noto Sans SC，按字重做子集化），或显式指定一个 CJK 无衬线字体族，使全 App 字体在任意设备上一致。改完这一项，观感提升超过本报告其他所有条目的总和。

### 3.2 P1 · 体验断层与一致性崩坏

#### A 组 · 设计系统未被执行

**P1-1｜字号阶梯倒挂，且被绕过约 4 倍**
【证据】`Type.kt`：titleLarge 22 > headlineLarge 20 > headlineMedium 18，语义倒挂；83 处硬编码字号 vs 22 处 typography，混入 10/11/13/15sp 体系外尺寸；首页单屏 6 种字号。
【建议】重排阶梯使其单调递增（display > headline > title > body > label），相邻层级差拉到至少 2sp 并扩大整体跨度；建立"只用这 12 个字号"的硬约束，将现有 83 处逐一归位到最近档位。凡找不到对应档位的，说明阶梯缺档，应补档而非就地写数字。

**P1-2｜形状体系碎片化**
【证据】`Shapes.kt` 定义 5 档（4/6/8/12/20dp），全 App 仅 **4 处**引用；同时存在 **69 处硬编码圆角**，散落 7 种取值（2/4/6/8/12/20/24dp）。同类"头部卡片"在消息页 8dp（`MessageScreen.kt:46`）、我的页 12dp（`MineScreen.kt:60`）。
【建议】收敛到 3 档（小/中/大），全量替换 69 处硬编码。2dp 与 24dp 各仅出现一两次，属特例，并入相邻档位。

**P1-3｜语义色 token 全为死代码，订单状态无视觉差异**
【证据】`PriceColor` / `StarColor` / `SuccessColor` / `WarningColor` / `DividerColor` **5 个 token 零引用**；价格改用 `colorScheme.error` 渲染（`HomeScreen.kt:231`、`MyOrdersScreen.kt:52`、`OrderDetailScreen.kt:38`），深色下因此变为粉色；订单五态全部用 `primaryContainer`（`MyOrdersScreen.kt:48`、`OrderDetailScreen.kt:35`），"已取消"在深色下成为整卡最亮元素。
【建议】给订单状态一套独立的五色语义板（待付款=警示橙、已付款=信息蓝、已发货=主色、已完成=成功绿、已取消=中性灰），并保证每色都有暗色变体。价格回归独立的"价格红"token，不再借用报错红。**清理 Color.kt 中的死 token 或让其真正生效——留着不用比删掉更危险**，下一个人会以为它已经在生效。

**P1-4｜表单范式两套并存**
【证据】登录 / 注册 / 发布页使用框架内的浮动标签；意见反馈页使用"反馈类型""反馈内容"这类框外段落标题（`FeedbackScreen.kt`）。字段间距也不一致（12dp vs 16dp），提交按钮位置不一致（6 个页面用顶栏文字按钮，下单页用底部实心按钮）。
【建议】统一一套表单范式：确定标签形态（框内浮动 / 框外标题二选一）、字段间距、必填标记、错误位、提交按钮位置，抽成共享的表单组件。

**P1-5｜列表行/设置行三套实现**
【证据】设置页为 `ListItem` 包裹在 `Card` 内 + 分组标题（`SettingsScreen.kt:49-79`）；我的页为裸 `ListItem` + 分隔线、无分组（`MineScreen.kt:102-106`）；关于页为裸 `ListItem`（`AboutScreen.kt:30-32`）；主题模式页又是自定义 `Row` + RadioButton（`ThemeSettingsScreen.kt:36-42`）。
【建议】统一为一种设置行组件，明确"是否分组、是否用卡片、图标样式、分隔线缩进"四个参数。

**P1-6｜"退出登录"等同类操作在不同页面长相不同**
【证据】我的页是胶囊描边按钮（`MineScreen.kt`），设置页是裸的居中红字（`SettingsScreen.kt:83`）。搜索框在首页为 8dp 方角、在搜索页为近胶囊圆角。
【建议】同一语义的操作与组件在全 App 只有一种外观。

#### B 组 · 深色模式

**P1-7｜表面色阶失效，"卡片"概念在深色下消失**
【证据】`Color.kt:45` `DarkBackground` 与 `:47` `DarkSurface` 取值完全相同（`0xFF1A1C1E`）；`Color.kt:51-52` 定义的 `DarkSurfaceContainerLow/High` 未被 `Theme.kt:19-27` 的 `darkColorScheme` 接收，同为死代码。截图显示深色下卡片与背景几无色差。
【建议】给深色模式一套真正递进的表面色阶（背景 / 卡片 / 卡片上的浮层三级，每级至少 4-6 点明度差），并把 surfaceContainer 系列真正接入 colorScheme。**这是深色模式修复的第一优先级。**

**P1-8｜系统导航栏不跟随 App 内深色主题**
【证据】15 张深色截图 **100% 复现**：App 纯深色，系统导航条浅灰白底 + 深色图标。根因：`MainActivity.kt:19` 的 `enableEdgeToEdge()` 按系统主题决定系统栏样式，而 App 内主题独立设置。
【建议】在主题切换时主动设置系统栏（状态栏与导航栏）的图标明暗与背景，不依赖系统默认值。

**P1-9｜深色模式其余配置问题**
【证据】① `SkeletonCard.kt:33` shimmer 硬编码浅灰 `#E0E0E0 → #F5F5F5`，深色下闪出亮块；② `themes.xml` 父样式锁死 `android:Theme.Material.Light.NoActionBar`，切深色后窗口背景仍为浅色，启动/重建白闪；③ 色板缺 `DarkSuccessColor` / `DarkWarningColor`。
【建议】shimmer 改为由主题表面色派生；窗口背景主题与 App 内设置联动；补齐缺失的暗色 token。深色模式建议作为一次完整走查任务，而非逐 bug 修补。

**P1-10｜分类色板失控（亮色下杂乱、深色下霓虹）**
【证据】颜色来自服务端 hex（`GoodsModels.kt:69-76`），8 个分类 7 种颜色、无语义逻辑、与品牌主色无关，"其他"为灰色呈禁用态。深色模式下这些高饱和色块铺在纯黑上成为全屏最亮元素。截图实锤对比度失败：分类页"考研资料"浅绿块 + 白图标几乎不可见（`6bb63ee5`）。
【建议】分类色收敛为受控色板且**同时提供亮/暗两套值**；或改为中性底色 + 彩色图标，把颜色留给真正需要语义之处（价格、状态）。"其他"使用中性色而非暗灰色。

**P1-11｜亮色 banner 在深色下刺眼**
【证据】首页营销图为高明度蓝白色调，深色模式下成为发光板（`7849f33d`）。
【建议】为深色模式准备暗色版 banner，或在深色模式下叠加压暗遮罩。

**P1-12｜深色下选中态降级**
【证据】「我的订单」tab 深色下三个文字全为白色，选中态仅剩一条下划线（浅色下为蓝色文字 + 下划线）。
【建议】深色模式下选中态必须同时依靠颜色区分，而非仅靠细线。

#### C 组 · 状态与反馈

**P1-13｜反馈层只有 Toast（92 : 0）**
【建议】将反馈分为三类各归其位：**字段级错误**留在输入框下方（行内）；**操作结果**用可带操作按钮的提示条（支持撤销）；**全局性/持久性错误**（如登录态失效）用页面级错误块。Toast 只保留给"复制成功"这类瞬时、无需行动、不影响任务的确认。

**P1-14｜错误信息笼统且与字段脱钩**
【证据】全 App 仅 2 处行内错误（`RegisterScreen.kt:67,69`），其余一律底部 Toast，文案多为"操作失败"级别，服务端原始字符串直接透给用户。
【建议】错误信息必须回答"哪里错了、为什么错、怎么改"三件事。手机号格式错误就写在手机号输入框下方并说明正确格式；不透传服务端原始字符串。

**P1-15｜聊天无发送态、失败丢草稿、无已读、时间戳被裁切**
【证据】发出即清空输入框（`ChatScreen.kt:157`），WebSocket 无回执；`MessageInfo.isRead` 存在但不渲染；新消息无条件强制滚到底（`:106`）；空会话无占位（`:264`）；**截图实锤**：`12b783be` 中"下午 15:32"时间戳只显示上半部分，下半被输入区压住。
【建议】① 消息增加"发送中 / 已发送 / 失败-可重试"三态，失败时草稿保留在输入框；② 渲染已读回执；③ 仅在用户本就在底部附近时才自动滚动，否则给出"新消息"浮标；④ 空会话给引导文案；⑤ 修正输入区与消息列表的边界处理。聊天是这类品类的成交现场，商业价值高于实现成本。

#### D 组 · 导航

**P1-16｜Tab 切换丢状态**
【证据】四个 tab 均用 `popUpTo(Home)` 且不保存/恢复状态（`NavGraph.kt:117-121` 等四处）。
【建议】切换 tab 时保留各 tab 的滚动位置与列表状态。"逛—比较—回退再逛"是本 App 的主循环。

**P1-17｜认证流程不统一 + 四处死返回键**
【证据】4 个入口 3 套头部 5 种返回策略（详见 2.3）；`ResetPasswordScreen.kt:46`、`VerifyScreen.kt:110`、`ChangePasswordScreen`、`ChangePhoneScreen` 四处返回无兜底，深链进入时按返回无反应。
【建议】四个入口统一为同一套骨架（同样的头部结构、标题层级、返回兜底逻辑）。返回键必须有兜底目标。

#### E 组 · 无障碍

**P1-18｜触控目标小于 48dp（15 处以上）**
【建议】视觉尺寸可保持精致，但**点击热区一律扩到 48×48dp**（图标周围补不可见内边距）；文字型操作用最小高度约束而非让文字本身当热区。这项是纯增量改动、零设计风险，建议优先做。

**P1-19｜图片缺少有意义的描述**
【证据】`contentDescription = null` 17 处 vs 有意义的描述 7 处。商品封面、banner、证件照、聊天图片、聊天头像全部无描述。
【建议】为承载信息的图片补描述；纯装饰性图标保持 null。

**P1-20｜表单无障碍几乎为零**
【证据】42 个输入框无一处 autofill / 密码管理器语义、无一处 IME action；4 处验证码框用普通文本键盘；价格与手机号输入框无对应键盘类型。
【建议】① 输入框补 autofill 语义（直接影响登录转化率）；② 补回车跳转/提交；③ 验证码、手机号、价格接对应键盘类型；④ 证件号类输入另加"不自动纠正、不记忆"处理。

**P1-21｜协议链接不可辨识、复选框语义断裂**
【证据】《用户协议》《隐私政策》与正文同色同字重，看不出可点（截图 `bfe44aa0` 确认）；复选框与文字是两个互不关联的可点控件（`RegisterScreen.kt:73-75`）。
【建议】协议名用可辨识的链接样式；复选框与文字合并为单一语义控件。

**P1-22｜67 处自定义可点击元素缺按钮语义**
【证据】`Animations.kt:25` 的 role 默认值为 null，大量调用点未传。
【建议】统一声明按钮语义，读屏应播报"按钮"而非"可点击"。

#### F 组 · 内容呈现

**P1-23｜用户生成内容溢出与硬裁切**
【证据】`MyGoodsScreen.kt:81` 与 `HistoryScreen.kt:60` 设了 2 行上限但未设省略号 → 长标题被**硬切**、无省略提示；聊天文本气泡无宽度上限也无行数限制（`ChatScreen.kt:225`）；会话昵称无约束（`MessageScreen.kt:60`）；下单页商品标题、收货人、地址全部无约束（`CreateOrderScreen.kt:61,68,78`）。
【建议】所有用户生成的单行文本默认单行 + 省略号，多行文本默认上限 2 行 + 省略号，地址类允许 2-3 行；聊天气泡设最大宽度（约屏宽 70%）并允许长串强制换行。

**P1-24｜时间戳精确到秒**
【证据】会话列表 `2026-09-07 15:33:17`（`MessageScreen.kt`）、商品详情 `2026-06-18 15:00:00`（`GoodsDetailScreen.kt`）。
【建议】会话列表用相对时间（今天→"15:33"，昨天→"昨天"，更早→"9月7日"）；商品详情用"6月18日发布"。

**P1-25｜订单卡片把最没用的信息放在最显眼位置**
【证据】「我的订单」每张卡的第一行是 20 位订单号 `CF202606251823233858` + 状态标签（截图 `85e83973`），商品名与价格被推至下方。
【建议】卡片首行放商品标题或状态，订单号降到最后一行小灰字。同时降低价格的色彩权重——当前价格用鲜红、状态用蓝，两个高饱和大色块互相抢夺注意力。

**P1-26｜发布页"成色"滑块控件视觉破碎**
【证据】截图 `e389a5d9`（浅色）与 `6f98de41`（深色）显示该控件由四种互不相干的语言拼成：蓝色长胶囊轨道、轨道上十个白色小圆点、白色方块 + 蓝点的把手、把手左侧一根高出轨道的蓝色竖条。无任何档位文案，把手位置压在轨道右端之外。深色模式下轨道变为高亮浅蓝，更为刺眼。
【建议】成色是二手交易的核心字段（直接影响成交），值得单独设计。改用**分段选择器**（9档/8档…横向可滑的 chip 组）或**标准滑块 + 明确档位标签 + 两端极值文案**。任何情况下不要在轨道上撒点。

**P1-27｜"我的"页滚动时内容压在状态栏上**
【证据】截图 `8bcdee08`：该页顶部为自定义标题（`我的` + 齿轮）且可滚动，滚动后头像、昵称、手机号滑至状态栏下方，与时间、5G、电量图标重叠，两边都不可读。对比其他子页有 `GlassTopBar` 且带状态栏内边距，不出现此问题。
【建议】无固定顶栏的滚动页面，需在状态栏区域加不透明背景或滚动时淡入的遮罩，保证系统图标始终可读。

**P1-28｜实名认证"审核中"使用了一个永远转的加载圈**
【证据】截图 `eb897078` / `b894df6b`：蓝色 spinner + "审核中，请耐心等待" + "通常需要 1-2 个工作日"。
【建议】spinner 语义是"请等几秒"，而这里是等两天。用户会盯着它等且它永远转不停，看起来像卡死。静态状态应用静态视觉——时钟/沙漏/文档图标 + 明确状态标签 + 预计完成时间。

### 3.4 首轮代码推断 vs 截图验证对照

## 四、推荐设计方向

### 三个关键词

> ### 内容优先 · 状态完整 · 一套语言

#### 内容优先（Content First）

这个 App 卖的是"别人用过的实物"，视觉主角只能是商品图与价格。当前界面把大量视觉预算花在**不承载信息的装饰**上——描边、阴影、半透明、渐变投影——而真正需要被突出的价格、成色、校区反而与标题挤在同一档视觉重量里。

方向是**先做减法**：去掉不成立的玻璃、去掉 7 种圆角中的 5 种、去掉顶栏下方与底栏上方那两道无效渐变；然后用**色阶与留白**而非描边来建立层级——背景、卡片、卡片上的浮层用三个明确递进的表面色，而不是三层几乎一样的白。

这项在深色模式下尤为关键：当前 `DarkBackground` 与 `DarkSurface` 取同一值，导致深色下"卡片"这个层级完全消失。

#### 状态完整（Stateful by Default）

这是当前最大的缺口，也是投入产出比最高的一块。现在七个页面在白屏，92 处反馈靠 Toast，提交按钮一半没有进行中状态。

方向是确立一条验收铁律：**任何一个从网络取数的页面，都必须能回答"加载中长什么样、没有数据长什么样、出错长什么样"。**

落地时先解决 P0-4 / P0-5 / P1-13 / P1-14——补齐三态、防重复提交、把反馈从 Toast 分层为"行内错误 / 可撤销提示条 / 页面级错误块"。做完这部分，App 的完成度观感会有质变，且完全不需要改动视觉风格。

#### 一套语言（One System）

审计中最刺眼的一组数字是：83 处硬编码字号 vs 22 处 typography；69 处硬编码圆角 vs 4 处 shapes 引用；5 个语义色 token 零引用；订单五个状态同一个颜色；深色下背景与表面取同一个值。

**不是没有系统，是系统被绕过了。**

方向不是再建一套新规范，而是**让已有的一套真正生效**：修好倒挂的字号阶梯、把 69 处圆角收敛回 3 档、给订单状态一套五色语义板、把表面色阶接进 colorScheme、把字体固定下来、让玻璃只出现在它成立的地方（或整体去掉）。

**一套被执行的普通规范，价值远高于一套被绕过的精致规范。**

### 落地顺序建议

| 阶段 | 内容 | 理由 |
|---|---|---|
| **第 1 周** | P0-7 字体、P0-1 验证码、P0-5 防重复提交、P1-18 触控目标 | 全是低风险改动，不动视觉、不涉及设计决策，可并行开工。P0-7 单项收益最大 |
| **第 2 周** | P0-2 键盘、P0-3 状态保存、P0-4 补三态、P0-6 危险操作确认 | 工作量最大、体验收益也最大的一块，建议集中做 |
| **第 3 周** | P1-1~P1-6 设计系统收敛、P1-7~P1-12 深色模式、P1-19~P1-22 无障碍 | 需要设计决策，建议先定规范再批量改 |
| **第 4 周** | P1-23~P1-28 内容呈现、全部 P2、深色模式完整走查 | 打磨与一致性收尾 |

### 需要拍板的三件事

1. **玻璃拟态是去是留？** 唯一需要产品层面决策的设计方向问题。留，就要让内容从栏下方滚过；去，就要接受顶栏底栏变为实色。两边改法完全不同。
2. **订单状态色板愿意引入几种颜色？** 当前全 App 只有蓝/红/灰三种语义色，做五态区分必然要引入橙、绿——`Color.kt` 里其实已经定义，只是没用。
3. **发布页要不要做草稿？** P0-3 中最重的一块。做草稿体验最好但工作量最大；只做"返回前确认"成本低很多。
